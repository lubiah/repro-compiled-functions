# `compiledFunctions` keys depend on module evaluation order

Minimal reproduction for MikroORM 7.2.1: `compiledFunctions` (the documented way to run on
eval-free runtimes such as Cloudflare Workers) is keyed by `uniqueName`, which embeds
`EntityMetadata._id` — a process-global counter assigned when the entity modules are *evaluated*,
not when `MikroORM.init` reads the `entities` array.

Any entry point that evaluates those modules in a different order than the `mikro-orm compile` run
did asks for keys that are not in the generated file. Every lookup then misses and falls back to
`new Function`, which is an `EvalError` on eval-free runtimes and a silent performance cliff
everywhere else.

Same code, same config, same entities — only the import order changes.

## Requirements

Node >= 20 (or Bun). **No database is needed**: the config sets `connect: false`, so
`MikroORM.init` only performs metadata discovery — which is exactly what triggers the code
generation that fails.

## Steps

```bash
npm install                 # or: bun install
npm run compile             # mikro-orm compile --config ./src/orm.config.js
npm run order-1             # entities evaluated a, b — same order as the config
npm run order-2             # entities evaluated b, a — a bundler is free to do this
npm run order-2-eval-free   # order-2 with `new Function` disabled, like workerd
```

`src/compiled-functions.js` is generated by `npm run compile` and is gitignored, so run step 2 on a
fresh clone. It contains `pkGetter-a_0` and `pkGetter-b_1000` — the keys of the *first* order only.

## Observed (Node v26.0.0, MikroORM 7.2.1)

```
$ npm run order-1
uniqueNames: b_1000, a_0
compiled-function misses: 0 (all keys found)

$ npm run order-2
uniqueNames: b_0, a_1000
compiled-function misses: 6 -> e.g. pkGetter-b_0

$ npm run order-2-eval-free
return function(entity) {
  return entity.id;
}
init threw: EvalError: Code generation from strings disallowed for this context
```

The third run prints the generated source (from `Utils.createFunction`'s `console.error(code)`)
followed by the `EvalError` thrown inside `MikroORM.init` — the same failure shape as on
Cloudflare Workers.

## Why this happens

- `EntityMetadata._id = 1000 * EntityMetadata.counter++` — `@mikro-orm/core/typings.js:40` — a
  static counter that is never reset (`MetadataStorage.clear()` does not reset it either).
- `get uniqueName() { return this.tableName + '_' + this._id }` — `typings.js:195`.
- Cache keys: `pkGetter-${meta.uniqueName}` (`utils/EntityComparator.js:98`, same pattern at
  150/209/239/423/689), `pkSerializer-`, `pkGetterConverted-`, `snapshotGenerator-`, `comparator-`,
  `resultMapper-`, and `hydrator-${meta.uniqueName}-${type}-${normalizeAccessors}`
  (`hydration/ObjectHydrator.js:410`).
- `defineEntity()` builds an `EntitySchema`, whose constructor constructs `EntityMetadata` eagerly
  (`metadata/EntitySchema.js:34`), so `_id` is stamped when the module is **evaluated** — before
  `MikroORM.init` ever looks at `entities`.
- `Utils.createFunction` (`utils/Utils.js:738`) does
  `if (key && compiledFunctions?.[key]) … else new Function(...)`, and only logs the generated code
  if `new Function` itself throws — so a key mismatch is indistinguishable from
  "no `compiledFunctions` supplied" until the runtime refuses codegen.
- `MikroORM.init` re-runs discovery on every call (`MikroORM.js:87-99`), so nothing re-anchors the
  ids either.

Regenerating `compiled-functions.js` does **not** fix it: that reproduces the *generator's* order,
and the user cannot control the order a bundler (or a second entry point, or a second bundling
pass) evaluates modules in.

## Workaround

Overriding the getter makes the keys a pure function of the entity, so both sides agree regardless
of evaluation order; `mikro-orm compile` picks it up automatically because it loads the same config:

```js
import { EntityMetadata } from '@mikro-orm/postgresql';

const id_for = (key) => {
  let hash = 2166136261;
  for (const char of key) hash = Math.imul(hash ^ char.charCodeAt(0), 16777619);
  return 1000 * (1 + ((hash >>> 0) % 999_999)); // keep MikroORM's 1000 band: EventManager adds event types to _id
};

Object.defineProperty(EntityMetadata.prototype, 'uniqueName', {
  get() { return `${this.className}_${id_for(this.className)}`; },
});
```

Note the constraint: `uniqueName` is read **before** `tableName` is assigned — `MetadataStorage.set()`
keys `#uniqueNameMap[meta.uniqueName]` from `MetadataDiscovery.discoverReferences` — so the derived
value must be identical at every read. `className` is available that early; `tableName` is not.

## Suggested fixes

1. Warn (or throw in a strict mode) in `Utils.createFunction` when a `compiledFunctions` map is
   provided but the key is missing, naming the key and pointing at `mikro-orm compile`.
2. Derive `uniqueName` from a stable identity, or content-address the keys
   (`pkGetter-<entity>-<hash of the metadata shape>`), so a regenerated artifact is valid regardless
   of evaluation order.
3. `mikro-orm compile --verify`, asserting every discovered entity has its expected keys and that
   keys are unique.
